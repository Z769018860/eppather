# SANER 2027 methodology evidence: MaxMEMS search, loop ablation, and summary fidelity

Date: 2026-09-25

## 1. Path-sensitive memoization must be measured, not assumed

The stable MaxMEMS search is deliberately path-sensitive. Its current memo key is

```text
(CFG node, loop-unroll state, complete serialized path prefix)
```

The complete prefix is required by the current implementation because feasibility and complete-path MEMS can depend on earlier branch decisions and symbolic updates. Dropping the prefix without a proof of suffix equivalence can merge states with different feasible extensions; an earlier Lua summary experiment exposed exactly this class of defect.

This safety choice also means that memo reuse may be small. The `-g` mode therefore reports, per function:

- `[DP MEMO LOOKUPS]`
- `[DP MEMO HITS]`
- `[DP MEMO HIT RATE]`
- `[DP MEMO STORES]`
- `[DP MEMO ENTRIES]`
- `[DP TERMINAL EVALS]`
- `[DP TIME COST]`

The controlled witness experiment records those counters together with `[DFS TIME COST]`. The paper should describe this implementation as an **exact path-sensitive memoized search** rather than claiming a generic dynamic-programming speedup. A low hit rate is a scalability result, not a correctness failure.

Reproduce:

```bash
cmake -S . -B build_maxmems_witness -DANALYSIS_BACKEND=epat++
cmake --build build_maxmems_witness --target cnip -j2
python3 tools/maxmems_witness_experiment.py \
  --cnip "$PWD/build_maxmems_witness/cnip" \
  --output-dir maxmems-witness-results
```

The generated `summary.csv`, `summary.json`, and `summary.md` contain the DP/DFS timing and memo-reuse evidence.

## 2. Loop-summary ablation

The repository already contains a paired 20-subject summary-on/summary-off experiment in
`tools/evaluate_loopscc_integration.sh` and
`docs/loopscc-integration-effect-2026-09-16.md`.

Archived paired result:

| Metric | Result |
|---|---:|
| Completed A/B pairs | 20/20 |
| Equal solution-space counts | 20/20 |
| Equal weighted MEMS | 20/20 |
| SSA-applied cases | 0/20 |
| Ground-validated cases | 18/20 |
| Fallback cases | 2/20 |
| Summary-enabled total time | 9533 ms |
| Summary-disabled total time | 9630 ms |
| Enabled/baseline time ratio | 1.0102x |

Interpretation: the experiment supports semantic preservation for the tested bounded cases and shows conservative fallback. It does **not** demonstrate a performance improvement; the measured end-to-end difference is too small to distinguish from runner/process noise.

This ablation should be reported separately from the MaxMEMS search performance experiment.

## 3. Baseline positioning

The exact semantic baseline for the MaxMEMS objective is bounded exhaustive DFS using the same complete-path evaluator. It answers the same optimization question and is therefore the primary numerical baseline.

KLEE and WISE are useful related systems but are not drop-in numerical baselines for the same objective:

- KLEE is a symbolic execution/test-generation system whose default objective is path/coverage exploration rather than maximization of Eppather's source-level memory-access count.
- WISE targets generation of worst-case-complexity inputs with a different cost/search formulation.
- Classical unit-cost IPET is a structural upper-bound formulation unless feasibility constraints and Eppather's source-level cost model are encoded explicitly.

A future external-tool comparison should therefore replay the tests generated by the external tool under the same source-level MEMS instrumentation and report both attained maximum MEMS and analysis budget. It must not compare unrelated native metrics as if they were the same quantity.

For the current paper, use:

1. exhaustive DFS as the same-objective exact baseline;
2. summary-disabled execution as the loop-summary ablation;
3. KLEE/WISE/IPET as related-work baselines with an explicit non-equivalence statement unless a same-objective adapter is actually executed.

## 4. RQ3 should be a fidelity-boundary result

The archived 66-entry small-library evidence shows:

- direct source body: 0/30 positive estimates;
- simplified source: 2/11 positive estimates;
- compatibility model: 18/25 positive estimates;
- total: 20/66 positive estimates.

The three selected cJSON/Lua/tinyexpr values (15/21/20) are also obtained from compatibility-model slices.

Therefore RQ3 should not be framed as evidence that the summary pipeline accurately estimates the original projects. It is stronger and more defensible as a **source-fidelity boundary** result:

> How does source transformation affect whether the current summary pipeline produces a non-zero bounded MEMS estimate, and what fidelity limitations does that expose?

The conclusion should state that all direct-body slices in this study produce zero under the current recognition/modeling pipeline, while most positive values arise after simplification or compatibility modeling. Same-slice DP/DFS agreement validates the search on the transformed slice only; original-source estimation error remains unmeasured.
